## Corrections — 15 November 2026

Thirteen statements were checked against their primary sources and corrected.

- **Lamport is the ancestor of the hash-based family, not a part of SLH-DSA.** [FIPS 205](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.205.pdf) §3 builds SLH-DSA from FORS (few-time) and WOTS+ (one-time, at the XMSS leaves); the word "Lamport" does not appear in it. The live demo is still real Lamport, and still the right place to see why a leaf may be signed once.
- **Rainbow's weekend break is the "simple attack".** Beullens, [*Breaking Rainbow Takes a Weekend on a Laptop*](https://eprint.iacr.org/2022/214) (Crypto 2022), names its own result the simple attack (§3) and credits the *rectangular MinRank* attack to his earlier [ePrint 2020/1343](https://eprint.iacr.org/2020/1343) (Eurocrypt 2021). The 53-hour figure is the paper's own, for the second-round SL 1 parameters.
- **Prange succeeds on an error-free information set.** C(n−k, t) / C(n, t) is the probability that a random information set contains *none* of the t errors, not all of them.
- **ML-KEM's lattice is 512 to 1,024 dimensions.** [FIPS 203](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.203.pdf) Table 2 sets the ring degree n = 256 and the module dimension k ∈ {2, 3, 4}; the lattice dimension is k·256.
- **SIKE was never a finalist.** [NIST IR 8545](https://nvlpubs.nist.gov/nistpubs/ir/2025/NIST.IR.8545.pdf) §2.1: of the four fourth-round KEMs, Classic McEliece was the third-round finalist and BIKE, HQC and SIKE were alternates. Rainbow was the multivariate third-round finalist.
- **The uov-Ip row shows Round-3 sizes, so it says so.** The row's (119, 45, 256) figures are the [UOV specification version 3.0](https://csrc.nist.gov/csrc/media/Projects/pqc-dig-sig/documents/UOV_Specification_R3.pdf) (30 August 2026, the Round-3 submission), Table 1: a 321,300 B expanded public key, a 278,087 B expanded secret key and a 135 B signature. The row carried the Round-2 figures — (112, 44, 256) with 278,432 / 237,896 / 128 B, from [version 2.0](https://csrc.nist.gov/csrc/media/Projects/pqc-dig-sig/documents/round-2/spec-files/uov-spec-round2-web.pdf) (February 2025) Table 1 — under a “Round 2” label until 2026-11-18, which was honest but a round behind. Both sizes are derived rather than copied: |epk| = m·n(n+1)/2 and |esk| = 32 + vm + m·v(v+1)/2 + m·vm with v = n − m reproduce 321,300 and 278,087 exactly, so a mistyped table cell cannot pass. The note still records the Round-2 values, because a reader meeting them elsewhere needs to be able to place them.
- **The multi-target analysis is PKC 2016, not 2020.** IACR CryptoDB lists Hülsing, Rijneveld and Song, *Mitigating Multi-target Attacks in Hash-Based Signatures*, in the PKC 2016 program; the preprint is [ePrint 2015/1256](https://eprint.iacr.org/2015/1256). `Attack` is documented to carry the first peer-reviewed venue year, and the entry now cites the venue alongside it.
- **SQIsign level-I sizes are 83 / 270 / 200 bytes.** [SQIsign specification version 3.0](https://sqisign.org/spec/sqisign-20260901.pdf) (1 September 2026, the Round-3 submission), Table 12: public key 83 B, secret key 270 B, signature 200 B. The row previously carried the Round-1 figures.
- **SQIsign's timings are the specification's own, on the platform it names.** The row printed "keygen ≈ 1B · sign ≈ 2B · verify ≈ 50M cycles (early ref impl, Skylake)" and "signing ≈ seconds", neither of which appears in any current specification. [Version 3.0](https://sqisign.org/spec/sqisign-20260901.pdf) Table 13 — "SQIsign performance in 10⁶ CPU cycles on an Intel Core i7-13700K CPU. Results are the median of 1,000 benchmark runs" — gives NIST-I **32.2 / 93.9 / 12.1** for the assembly-optimized build for Intel Broadwell or later, and §1.1 gives the wall clock itself: "about 27.6 ms for signing and 3.6 ms for verification on an Intel Core i7-13700K". Both are quoted as printed; no cycle count was converted to a time and nothing was rescaled. The "103.0 Mcycles / 5.1 Mcycles" in §1.3 is deliberately *not* used — it describes the round-2 version against round 1, not the current build.
- **Round 3 is dated where the lab states a scheme's status.** [NIST IR 8610](https://doi.org/10.6028/NIST.IR.8610) (May 2026): "The second round began on October 24, 2024, and continued until May 14, 2026", and NIST "selected nine candidate algorithms to move forward to the third round of evaluation". UOV and SQIsign are among them, so every place this lab gives their current status now carries **14 May 2026** and the IR 8610 citation. Process status and parameter version remain separate facts: since 18 November the uov-Ip row has used the Round-3 version 3.0 sizes, while its note preserves the earlier Round-2 figures for comparison.
- **Every OpenSSL cell is held to an OpenSSL document.** **Standards reviewed 15 November 2026.** [OpenSSL 3.5.0 release notes](https://openssl-library.org/news/openssl-3.5-notes/): "Major changes between OpenSSL 3.4 and OpenSSL 3.5.0 [8 Apr 2025] … Support for PQC algorithms (ML-KEM, ML-DSA and SLH-DSA)", so those three are shipped rather than experimental. [OpenSSL 3.6.0 release notes](https://openssl-library.org/news/openssl-3.6-notes/): "Major changes between OpenSSL 3.5 and OpenSSL 3.6.0 [1 Oct 2025] … Added LMS signature verification support as per SP 800-208." The [OpenSSL 4.1 default-provider algorithm list](https://docs.openssl.org/4.1/man7/OSSL_PROVIDER-default/) names ML-KEM-512/768/1024, ML-DSA-44/65/87, all twelve SLH-DSA parameter sets and LMS — and no Falcon / FN-DSA, HQC, BIKE, Classic McEliece or XMSS at all. Two consequences. **Falcon-512's "experimental" mark is removed**: it rested on the third-party oqs-provider, and a scheme reachable only through a separate provider is not OpenSSL support. **The stateful row is disclosed rather than papered over**: [EVP_SIGNATURE-LMS(7)](https://docs.openssl.org/4.1/man7/EVP_SIGNATURE-LMS/) says "The OpenSSL providers only support LMS signature verification" and "LMS support is disabled by default at compile-time. To enable, specify the enable-lms build configuration option", so of XMSS and LMS OpenSSL has only LMS, only verification, and only behind a build flag — which one glyph on a row named for two schemes cannot say, and the footnote now does. The column header is **OpenSSL 4.1** rather than "OpenSSL 3.x", because 3.0–3.4 have none of these algorithms and 4.1.0 / 4.0.3 are the current releases beside the 3.5.9 LTS.
- **KyberSlash reached a peer-reviewed venue.** IACR TCHES 2025(2):209–234, [doi:10.46586/tches.v2025.i2.209-234](https://doi.org/10.46586/tches.v2025.i2.209-234), CHES 2025 Best Paper.
- **Delfs–Galbraith circulated as arXiv:1310.7789**, not ePrint 2013/506 — that number belongs to Rauzy and Guilley, *A Formal Proof of Countermeasures Against Fault Injection Attacks on CRT-RSA*. The Sources entry already linked the arXiv preprint.

Four further figures that disagreed with the numbers printed beside them were also reconciled: the NIST process ran four rounds **2016–2025** (IR 8545 closed the fourth round in March 2025); Classic McEliece key generation is **tens of milliseconds**, which is what ≈ 150M cycles means, not seconds; and the ML-KEM-768 cycle counts are now the [Kyber team's own AVX2 table](https://pq-crystals.org/kyber/index.shtml) with its platform named (Haswell Core-i7 4770K: 52,732 / 67,624 / 53,156). The uov-Ip expanded secret key is **237,896 B** — the figure in the Round-2 specification's own size table and the one the size formula gives. With v = n − m = 112 − 44 = 68 over F₂₅₆, esk = (seed_sk, O, {Pᵢ⁽¹⁾, Sᵢ}): 32 + 68·44 + 44·(68·69/2) + 44·(68·44) = 32 + 2,992 + 103,224 + 131,648 = **237,896**. The 237,912 previously shown is no specification's value.

## What It Is

A high-level, interactive overview of the five major post-quantum cryptography (PQC) families: lattice-based, code-based, hash-based, multivariate, and isogeny-based. Where the rest of the crypto-lab portfolio drills into individual schemes, this demo zooms out to compare the families against one another — their underlying hard problems, representative schemes, public-key and signature sizes, NIST standardisation status, and the tradeoffs that decided which families won the first round of standardisation. The Rainbow signature scheme and SIKE key exchange were broken in practice in 2022; other multivariate and isogeny schemes continue in research. Everything runs client-side with no dependencies; the comparison corpus lives in a single typed data module.

## When to Use It

- **Teaching or briefing on PQC** — a one-screen map of the whole landscape before diving into any single algorithm.
- **Choosing a family for a migration** — compare key sizes, what each family provides (KEM vs signature), and maturity at a glance.
- **Understanding why lattices won** — see the balance of size, speed, and versatility that made ML-KEM and ML-DSA NIST's primary picks.
- **Explaining algorithmic diversity** — show why code-based and hash-based schemes exist as conservative backups even though lattices lead.
- **Do NOT use these figures for production parameter selection** — sizes are representative and rounded for teaching; consult the relevant FIPS or specification and a vetted library.

## What Can Go Wrong

- **MAYO research update — 16 November 2026.** [Li and Tao, *Extending the Schur–Macaulay Framework for UOV Attacks via Truncated Polynomial Algebras*, ePrint 2026/2444](https://eprint.iacr.org/2026/2444), revised 16 November 2026, reports lower attack-cost estimates for selected additional Round-3 MAYO parameter sets. This is a **preprint; conditional extrapolation** based on conjectural Hilbert-series and structured-rank predictions, not demonstrated production-key recovery. It does not establish the security of historical Round-2 sets or tiny teaching keys. The demo does not execute this attack. See **Multivariate → Attacks**, with the paper under **Sources**.

- **UOV structural-attack estimates — 14 November 2026.** [Li and Tao, *Attacking UOV-based Signatures over divided power algebras*, ePrint 2026/2272](https://eprint.iacr.org/2026/2272), revised 14 November 2026, is a **preprint; conditional extrapolation**. Its estimates for selected Round-3 UOV parameters depend on conjectural Hilbert-series predictions supported by small-instance experiments, not demonstrated production-key recovery. Its parameters differ from this lab’s uov-Ip comparison row, which moved to the Round-3 parameter set on 2026-11-18; the word “older” was dropped rather than replaced with a claim that the sets now coincide, which would need the paper read. The estimates must not be transferred to that row or to tiny teaching keys either way. This lab does not execute the divided-power wedge attack. Open **Multivariate → Attacks**, then **Sources** for the paper.

- **Physical faults during ML-KEM key generation — November 4, 2026.** [Kumar et al., *Keyber*, ePrint 2026/2766](https://eprint.iacr.org/2026/2766) is a preprint reporting end-to-end ML-KEM-512 key recovery on an ARM Cortex-M4 using one overclock fault during key generation followed by decapsulation queries to the faulty key. The authors analyze all parameter sets, but the physical demonstration is for ML-KEM-512. This attack requires physical fault access and an oracle; it is not a public-key-only mathematical break of ML-KEM. The lattice family's **Attacks** and **Sources** views cite it. This comparison does not reproduce the hardware experiment, and FIPS 203 remains final.

- **Hash-based assumptions do not prevent power leakage — 24 October 2026.** [Carrera Rodriguez et al., *SHAKEing SLH-DSA with Non-profiled SCAs*, ePrint 2026/2584](https://eprint.iacr.org/2026/2584), received 21 October and approved 24 October 2026, is a **preprint; attack-model-conditional**. The authors report full secret-seed recovery using non-profiled correlation power analysis on SLH-DSA-SHAKE on a 32-bit microcontroller, enabling forgery. This requires physical power measurements; it is not a mathematical break of SLH-DSA or SHAKE and does not establish vulnerability of SHA-2 browser implementations. The hash-based family now distinguishes mathematical assumptions from implementation security, with the source in its **Attacks** and **Sources** views. This comparison does not reproduce the experiment; SLH-DSA retains its standardized status.

- **SHA-2 power leakage — revised 20 November 2026.** [Chang et al., *Correlation Power Analysis on SHA-2-Based SLH-DSA*, ePrint 2026/2753](https://eprint.iacr.org/2026/2753) is a preprint reporting physical measurements on an STM32F303 Cortex-M4. The paper reports two distinct results: the baseline measures conditional stage-wise recovery with preceding secrets supplied correctly; the revision also chains recovered values to recover the full seed in all nine WOTS+ compression-round seed–signature cases per parameter set (three seeds with three signatures each). These measurements use individual PRF calls, not continuous signing traces; call identification and segmentation in a full signing trace remain unvalidated. This is not a mathematical break or evidence that the browser demo is vulnerable. Find the note under **Hash-based → Attacks**, with the paper under **Sources**.

- **Deterministic-CSIDH fault research — 20 October 2026.** Deterministic execution can make the same secret-dependent step easier to target repeatedly. Banegas, Dimitrova and Trimoska study fault attacks on deterministic CSIDH variants and OSIDH-LD. They recover full OSIDH-LD keys in software fault simulation and separately demonstrate a targeted instruction skip on ChipWhisperer-Lite hardware. This is not complete hardware key recovery or a public-key-only mathematical break of CSIDH. The result requires targeted fault injection and output observations; it is distinct from the SIDH/SIKE mathematical break. [Banegas, Dimitrova and Trimoska, *From if to Oops: Turning a conditional into a key-recovery oracle*, ePrint 2026/2542](https://eprint.iacr.org/2026/2542), received 19 October and approved 20 October 2026. **Preprint; attack-model-conditional.** This lab does not implement the attacked variants or reproduce the fault experiment.

- **Mathematical hardness does not prevent implementation leakage.** [Kim et al., *Power Analysis on SQIsign via Ideal Reconstruction from Quaternion Leakages* (ePrint 2026/2508)](https://eprint.iacr.org/2026/2508), received 16 October and published 17 October 2026, is a **preprint** reporting key recovery from leaked intermediate values in Round-3 SQIsign signing, including partial leakage. The result is **attack-model-conditional**: it does not establish a public-key-only mathematical break of SQIsign or a break of CSIDH. This lab does not implement SQIsign or reproduce the reported power analysis.
- **Falcon key-expansion leakage — revised 16 November 2026.** Li, Ma, Dou and Guo report complete key recovery from one power trace on PQClean Falcon-512 sign_dyn on ARM Cortex-M4 at -O0, -Os and -O3. In their separate optimized assembly experiment, ten traces recovered 53 of 100 test keys. The leakage occurs during secret-key expansion, before Gaussian sampling. These measured results require physical power observation of the evaluated implementations; they do not establish a mathematical break of Falcon or FN-DSA, or a vulnerability in this browser build. This lab does not reproduce the hardware attack. [Li et al., *One Fell Swoop*, ePrint 2025/2159](https://eprint.iacr.org/2025/2159), accepted to TCHES 2027; demonstrated result under a specific attack model. Find the note under **Lattice-based → Attacks**, with its citation under **Sources**.

- **Confusing implementation leakage with a broken lattice assumption** — [Zhou et al. (ePrint 2026/2124, September 22, 2026)](https://eprint.iacr.org/2026/2124) report Falcon power-trace key recovery on PQClean/ARM Cortex-M4; [Jahandideh (ePrint 2026/2137, September 22, 2026)](https://eprint.iacr.org/2026/2137) studies one-trace ML-KEM key-generation leakage on optimized Cortex-M4. These target-specific results do not change FIPS 203's final status or show a generic mathematical break.
- **Treating "post-quantum" as permanent** — Rainbow (multivariate) and SIKE (isogeny) were both broken in 2022; selecting a family on reputation alone is risky, which is why NIST standardised a diverse portfolio.
- **Assuming age rules out structural cryptanalysis** — Classic McEliece has no demonstrated practical production break, but [Weis (ePrint 2026/1984; version 0.5; revised October 6, 2026)](https://eprint.iacr.org/2026/1984) estimates key recovery below generic ISD costs for its candidate sets under explicit heuristics. Its public keys also measure hundreds of kilobytes, which can be prohibitive for constrained protocols.
- **Confusing what a family provides** — hash-based schemes do signatures only and cannot perform key exchange; picking a family without checking KEM-vs-signature support is a common early mistake.
- **Reusing state in stateful hash-based signatures** — LMS and XMSS fail catastrophically if signing state is ever reused, a failure mode absent from the stateless SLH-DSA.
- **Skipping hybrids during migration** — deploying a young PQC scheme alone, rather than combining it with a classical algorithm, removes the safety net if the PQC scheme is later weakened.

## Real-World Usage

- **NIST FIPS 203 / 204 / 205** — the finalised standards for ML-KEM (Kyber), ML-DSA (Dilithium), and SLH-DSA (SPHINCS+), drawn from the lattice and hash-based families compared here.
- **HQC selection (2025)** — NIST's choice of a code-based KEM as an algorithmically diverse backup to lattice-based ML-KEM.
- **Hybrid TLS key exchange** — widespread deployments pairing X25519 with ML-KEM-768 so a connection stays secure as long as either component holds.
- **liboqs / Open Quantum Safe** — the reference open-source library implementing schemes across these families for experimentation and integration.
- **Harvest-now-decrypt-later mitigation** — organisations migrating long-lived secrets to PQC today, before large-scale quantum computers exist, because recorded ciphertext can be decrypted retroactively.

## For Cryptographers and Students

The lab includes five live, in-browser learning tools — every byte computed locally, no servers, no telemetry:

- **Live Lamport one-time signature demo** — Generate a real Lamport keypair — a 16 KB private key plus a 16 KB public key, 32 KB in all (256 digest positions × 2 halves × 32 bytes = 16,384 bytes each; sizes re-checked against `lamportKeygen` in `src/crypto.ts` on 15 November 2026) — using the browser's `crypto.subtle.digest('SHA-256', …)`. Sign any message you type, watch the 256-cell digest grid colour in by which key-half each bit reveals, then click **Tamper & verify** to see the verification fail. This is real working cryptography (1979 Lamport, the ancestor of the whole hash-based family — but not a component of SLH-DSA, which signs each message with FORS and authenticates it with WOTS+ at the leaves of its hypertree; FIPS 205 never mentions Lamport). Open DevTools — the bytes are real.
- **Key reuse, mounted rather than described** — **Sign a second message** with the same keypair and the page counts, from the two digests it just computed, exactly how many of the 256 positions now leak *both* private halves (the outlined cells), how many remain one-sided, and what that does to the forgery grind — typically from 2²⁵⁶ down to about 2¹²⁸. That is still far out of reach of a browser tab, so a second panel runs the *same* `lamportKeygen` / `lamportSign` / `lamportVerify` functions over a **deliberately truncated 12 / 16 / 20-bit digest**, where the grind finishes in a few hundred hashes: two signatures are published, the leaked halves are assembled, candidate messages are hashed until one is covered, and the forged signature is handed to the real verifier, which accepts it. The scale is a toy and is labelled as one on the page; nothing about the attack is simulated. A control step then takes a message the leak does *not* cover, fills the missing positions with the only halves the attacker holds, and the same verifier rejects it.
- **2D lattice visualizer** — drag the basis vectors b₁ and b₂; the demo redraws every integer-combination lattice point, the fundamental parallelogram, and the shortest non-zero lattice vector in real time. Lagrange–Gauss reduction runs **as a visible sequence**: step once, or run to the fixed point, and every iteration prints what it actually did — whether it swapped b₁ and b₂, the integer μ = ⌊⟨b₁,b₂⟩/⟨b₁,b₁⟩⌉ it rounded to, the norm b₂ fell to, and the resulting orthogonality defect — until μ comes out 0. A *Parallel (not a lattice)* preset shows the honest failure: a rank-1 pair reduces to the zero vector, and the trace says the input spans a line instead of presenting (0, 0) as a shortest vector. Numerical readout includes ‖b₁‖·‖b₂‖, det L, and the orthogonality defect — so "what changes between a good and a bad basis" is something you can *feel*.
- **Prange ISD work calculator** — sliders for code parameters (n, k, t) with live log₂-bits computation using the C(n, t) / C(n−k, t) ratio. Presets for three Classic McEliece parameter sets illustrate generic decoding work. This calculator models neither modern ISD nor the 2026 structural key-recovery estimate, and its output is **not** an overall security level or standardization analysis.
- **Handshake bytes calculator** — already covered above, but now with a **0 / 1 / 2 intermediate cert** toggle so the compounding cost of long PQC certificate chains is visible (each ML-DSA intermediate adds ~5 KB). Selecting a dead scheme — the **Broken combo** preset picks SIKEp434 and Rainbow (Ia) — opens a hand-off panel naming the cryptanalysis that ended it, quoted from this repo's own attack list, and links through to the sibling lab that actually runs the mathematics: [crypto-lab-isogeny-gate](https://systemslibrarian.github.io/crypto-lab-isogeny-gate/) for Castryck–Decru, [crypto-lab-multivariate](https://systemslibrarian.github.io/crypto-lab-multivariate/) for Beullens on Rainbow. This page can price a broken scheme's bytes; it cannot break it, and says so.

Every family panel additionally includes:

- A **formal hard-problem statement** in symbols (Module-LWE, syndrome decoding, MQ, supersingular isogeny problem) plus a "reduces from" note explaining the hardness pedigree.

- A **Notable cryptanalysis** timeline per family — Prange ISD, BKZ, KyberSlash, MDPC decoding-failure, Patarin / Kipnis–Shamir / Beullens, Castryck–Decru, Kuperberg — each with year and one-line summary.
- **Further reading** with canonical citations (Regev 2005, McEliece 1978, Patarin 1997, Jao–De Feo 2011, Bernstein et al., Beullens 2022, Castryck–Decru 2022) and stable links (FIPS 203 / 204 / 205, RFC 8391, RFC 8554, IACR project pages).
- A **NIST categories** tab explaining the effort floors (Cat 1 ≈ AES-128, Cat 3 ≈ AES-192, Cat 5 ≈ AES-256), a **dated RSA-2048 resource comparison** inside the Shor context tab: Gidney–Ekerå’s 2019 preprint / 2021 publication (~20M noisy physical qubits, ~8 h) alongside [Gidney’s 21 May 2025 preprint](https://arxiv.org/abs/2505.15917v1) (~1M physical qubits with slack, less than one week). The comparison keeps 1,409 active logical qubits separate from 1,537 including idle hot patches, records the hardware assumptions, and makes no Q-Day forecast, a real-world **implementation status table** mapping each scheme to its support in liboqs / OpenSSL / BoringSSL / BouncyCastle / CIRCL / RustCrypto, and a **glossary** at the bottom with one-line definitions of every term used (KEM, LWE, NTRU, Goppa code, MDPC, MQ, isogeny, Grover, IND-CCA2, hybrid, harvest-now-decrypt-later, FIPS rounds).

The isogeny Math pane distinguishes the [Delfs–Galbraith](https://arxiv.org/abs/1310.7789v1) full-graph Õ(p^(1/2)) discussion from its special F_p Õ(p^(1/4)) algorithm. Both are exponential in input bit length n = log₂(p); the special-case bound is not a generic supersingular bound. The [Childs–Jao–Soukharev](https://arxiv.org/abs/1012.4019v3) GRH-conditioned quantum result concerns ordinary horizontally isogenous curves and a class-group action, not unrestricted supersingular path finding. This is a comparison of those cited scopes, not a complete current algorithm survey.

## Tech

Vite + TypeScript, zero runtime dependencies. The comparison corpus, history timeline, and classical baseline live in a single typed module (`src/data.ts`); the UI is plain DOM in `src/ui.ts`. Dark mode throughout, log-scale charts with a metric switch, an interactive handshake-bytes visualiser, URL deep-linking, and number-key shortcuts. WAI-ARIA tablists with keyboard navigation throughout.

All of the mathematics — Lamport keygen/sign/verify, the leak and forgery machinery, the Prange
ratio, and Lagrange–Gauss reduction — lives in `src/crypto.ts` as pure functions, so the unit tests
and the page run the identical code. Gates:

```
npm run test      # vitest: SHA-256 KATs, Lamport round-trips and forgeries, ISD, reduction traces
npm run build     # tsc --noEmit + vite build
npm run test:a11y # playwright: e2e/a11y.spec.ts (axe, both themes) + e2e/demo.spec.ts (behaviour)
```

`e2e/demo.spec.ts` asserts the computed outcome of each exhibit *and* its failure path: the tampered
message is rejected, the leaked-both count equals the differing-bit count, the toy forgery is accepted
by the real verifier while the uncovered control is refused, each McEliece preset lands in the category
its binomial ratio implies, and the parallel basis is reported as not a lattice.
